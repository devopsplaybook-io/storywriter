# Users

## Registration

- [x] The first user to register is automatically granted the **admin** role.
- [x] Subsequent users can be added by the admin via the Admin page.
- [x] Users authenticate with username and password.
- [x] Passwords must be at least 8 characters (`PASSWORD_MIN_LENGTH`). The rule applies to registration, admin-created users and password changes; the login form only enforces it when creating the first admin account, so existing shorter passwords still work.

## Authentication

- [x] JWT-based session tokens stored in localStorage.
- [x] Session tokens are valid for `JWT_VALIDITY_DURATION` (30 days here; common-utils itself defaults to 1 hour) and are renewed whenever the web client re-validates the session on page load. The library caps any token at `JWT_SESSION_MAX_DURATION` (30 days from the first sign-in), so after that period the user signs in again.
- [x] Login page detects if the server is uninitialized and offers admin account creation.
- [x] Login failures are throttled per client IP + username: at most `RATE_LIMIT_LOGIN_MAX` failed attempts per `RATE_LIMIT_LOGIN_WINDOW_MS`; successful logins do not consume the budget, so one user's failures never lock out other users. Exceeding the budget returns HTTP 429 with `Retry-After` and `{ "error": "Too many login attempts, try again later" }`.
- [x] Behind a reverse proxy, `TRUST_PROXY` must be `true` so the throttle keys on the forwarded client address (X-Forwarded-For); it is `false` by default and must only be enabled when all traffic arrives through a trusted proxy (the bundled `config.json` enables it for the proxied deployment).

## Login with a Code

- [x] Optional cross-device sign-in, off by default (`LOGIN_CODE_ENABLED`). A signed-out device shows an 8-character code (from a 20-letter alphabet) and polls; an already-signed-in user approves it from Settings ("Log in on another device").
- [x] Codes rotate every 30 s with a 60 s grace window; a login request lives 5 minutes and tolerates at most 5 wrong attempts before it fails.
- [x] The approving device must hold an interactive session. API tokens are refused (HTTP 403 `FORBIDDEN`), so a leaked token cannot approve devices.
- [x] Redemption is single-use: polling returns the session once, and a second poll for the same request returns HTTP 409 `ALREADY_USED`.
- [x] Every login-code response carries `Cache-Control: no-store`. Codes, request tokens and session tokens are never logged.
- [x] The UI (login page and Settings) hides the feature unless the server reports it available via `GET /api/users/login-codes/capabilities`; when the flag is off those routes are not mounted (404) and the web app falls back to password login only.
- [x] Login-code traffic (create/poll/preview/approve/cancel) is not counted by the failed-password login throttle; password login and its throttle semantics are unchanged.
- [x] Requires the `users_login_codes` table, shipped as migration `init-0011` for both SQLite and PostgreSQL and applied at boot even while the flag is off.

## Password Change

- [x] A **Change Password** button in Settings opens a dialog.
- [x] The dialog collects current password, new password, and confirmation.
- [x] Server verifies the current password before applying the change.
- [x] The new password must meet the same 8-character minimum as registration, and the form communicates the requirement.

## API Tokens

- [x] Users can create API tokens from the Settings page (optionally with an expiry date).
- [x] API tokens are generated by the shared common-utils routes: the plaintext value is returned once and only its SHA-256 hash is stored in the `users_api_tokens` table.
- [x] Tokens can be used in the `Authorization: Bearer <token>` header for API authentication.
- [x] The full token value is shown only once at creation time; later views show the token name and last-used date (the token itself is never retrievable).
- [x] Tokens can be revoked (deleted) at any time.

### API Endpoints

| Method     | Endpoint                | Description                              |
| ---------- | ----------------------- | ---------------------------------------- |
| [x] GET    | `/api/users/tokens`     | List own tokens (no secret material)     |
| [x] POST   | `/api/users/tokens`     | Create a new token (plaintext shown once)|
| [x] DELETE | `/api/users/tokens/:id` | Revoke (delete) a token                  |

## Roles

- [x] **admin** — full access: manage users, create/edit/delete books, manage access (global bypass).
- [x] **user** — can create and manage their own books, access shared books.
- [x] **owner** — a user listed in `books.ownerId`; full access to that book, including managing access and deleting it. Owners are not a separate global role.

## Admin Page

- [x] Lists all users with name, role, and creation date.
- [x] Admin can change user roles.
- [x] Admin can add new users.
- [x] Admin can delete users (except themselves).
